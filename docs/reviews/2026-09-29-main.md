## Summary

This is spec 0009 (Revisão das decisões da IA pelo Preposto): the "Revisão da IA" filter, the decisions panel with confirm, priority correction with the asymmetric SLA rule, service correction, `ticket:corrected`, and the reassignment fixes. The core SLA rule (`montarSnapshotCorrecao`) follows the spec table exactly, and the priority and service atomic filters repeat the values they read. The management-only history actions are filtered in the query on both read paths. There are three problems to fix before merge. The AC-20 fix covers the breach marker but not the `SlaEscalation` insert, so a correction during a monitor cycle can leave an orphan escalation that stops the chamado from ever being marked breached again. `reassignTicketAction`'s atomic filter still does not repeat `assignedToUserId`. And the AC-21 step isolation is missing in a few places after the committed write.

## Major

### 🟠 The monitor can still create an orphan `SlaEscalation` from a stale read after a correction, `lib/sla-monitor.ts:119`, `:170`, `:229` (with `app/(dashboard)/gestao/actions.ts:413`)

**Problem**: AC-20 added the read `resolutionDueAt`/`responseDueAt` to the monitor's `updateOne` filter, but in each branch the monitor calls `tryCreateEscalation(...)` and sends notifications **before** that conditional update, with no check on the deadline. The monitor reads every chamado once at the top of the cycle (`lib/sla-monitor.ts:57`) and then walks them one by one, so the window is the whole cycle, not milliseconds. Take a chamado that the monitor read as breached (or at ≤20%) with the old deadline. If a "desce" (or a "sobe" that moved the deadline) runs its step 5 `deleteMany` before the monitor reaches that chamado, the monitor then:
1. inserts a fresh `breach_resolution` / `breach_response` / `warning_80`, which the correction already cleaned up and cannot clean up again;
2. sends admins a false "SLA estourou" notification and email;
3. has its `updateOne` miss the filter, as designed, so the marker stays `null`.

From the next cycle on, `escalationSet` holds `chamadoId:breach_resolution` and the unique index makes `tryCreateEscalation` return `false`. So when the **new** deadline really expires, the monitor never sets `resolutionBreachedAt` and never notifies anyone.
**Why it matters**: This is the case AC-20 was meant to close, and only half of it is closed. The result is a chamado that really breached its corrected deadline but never carries the breach marker, which the breach report and dashboard rely on, plus a false breach alert. This is contractual SLA data.
**Suggested fix**: In the two breach branches, run the conditional `updateOne` first and create the escalation and notifications only when `modifiedCount === 1`. For `warning_80`, which has no marker, re-check the deadline before inserting, for example a conditional `exists({ _id, 'sla.resolutionDueAt': resolutionDueAt })`. Add a test in which the correction's `deleteMany` runs between the monitor's batch read and its per-chamado processing.

### 🟠 `reassignTicketAction`'s atomic filter omits `assignedToUserId` (and `sla.responseStartedAt`), `app/(dashboard)/gestao/actions.ts:1478`

**Problem**: The filter is `{ _id, status: 'em atendimento', catalogServiceId }`. The action reads `currentAssignedId`, rejects a same-tech reassign against it, writes `previousName → newTech` into both history entries, and decides `sla.responseStartedAt` from the read value. None of those values is repeated in the filter. So two managers reassigning A→B and A→C at the same time both succeed. The last write wins (C), but B still gets `ticket:assigned` with a Notification and an email for a ticket that is not theirs. History and `correcao_gestao` then say "A → B" and "A → C" instead of "A → B → C". The review brief states the invariant: repeat every value read.
**Why it matters**: A technician is dispatched by email to a ticket assigned to someone else, and the audit trail is wrong. The priority and service corrections already guard against this. Reassignment is the one correction path that doesn't.
**Suggested fix**: Add `assignedToUserId: chamado.assignedToUserId` to the filter, plus `'sla.responseStartedAt': chamado.sla?.responseStartedAt ?? null`, since the payload depends on it. Add a DB test with two concurrent reassignments.

### 🟠 AC-21 step isolation is not applied everywhere after the committed write, `app/(dashboard)/gestao/actions.ts:424`, `:1497`, `:1523`

**Problem**: AC-21 says only step 1 decides the outcome, and every later step has its own `try`. Three calls sit outside any per-step `try`:
- `updateTicketPriorityAction`: `UserModel.findById(session.userId)` at line 424 runs after the update and before the notice.
- `reassignTicketAction`: `UserModel.findById(currentAssignedId)` at line 1497 runs right after the update.
- `reassignTicketAction`: `ChamadoHistoryModel.create({ action: 'reatribuicao_tecnico' ... })` at line 1523, marked "Passo 3 (existente, intacto)".

If any of these throws, the outer `catch` returns `{ ok: false }` although the correction or reassignment is already committed. The technician notice is skipped, no `[revisao-ia]` line is written, and in the reassignment case the raw `e.message` (a Mongo or Mongoose message) reaches the UI. The manager's natural retry then fails with "A prioridade informada já é a atual." or "Selecione outro técnico para reatribuir.".
**Why it matters**: This is the exact contract AC-21 sets. The tests cover failures only in the steps that are wrapped, so they don't catch it.
**Suggested fix**: Wrap each of these in its own `try` that calls `registrarFalha(...)`. Use a fallback name when the lookup fails, like `corrigirServicoAction` already does for its `gestorUser`.

## Minor

### 🟡 A failed technician veredito never shows up in the `[revisao-ia]` result, `app/(dashboard)/gestao/actions.ts:730-739`, `:1534`

**Problem**: `aplicarVeredito` catches everything internally and never throws (`lib/conversas/decisoes.ts:588-623`). So `registrarFalha('reatribuicao_veredito', ...)` in `corrigirServicoAction` is dead code, and reassignment has no hook at all. When the `tecnico` DecisaoIa update fails, the `[revisao-ia]` line still says `resultado: 'ok'`.
**Why it matters**: AC-17 and AC-21 rely on `parcial:<passo>` to make a decision that was left `divergente` findable. The only trace left is a separate `[conversa]` line.
**Suggested fix**: For this call, use `resolverDecisao` directly and check `ok`/`reason`, as step 4 already does for the service. Or have `aplicarVeredito` return a status.

### 🟡 "Desce com técnico" on a legacy SLA with no stored `resolutionTargetMinutes` adds the full new target, `lib/sla-snapshot.ts:196`

**Problem**: `const Tc = atual.resolutionTargetMinutes ?? 0` makes `Tn − Tc = Tn`, so an Admin lowering the priority of a legacy chamado gets `Dc + Tn`. That is roughly twice the window.
**Why it matters**: It extends a contractual deadline far beyond the rule in AC-9. The case is rare, but it lands on the exact path the Admin-only rule exists to control.
**Suggested fix**: When `Tc` is null, return `{ ok: false, motivo }`, or fall back to the snapshot computed from `classifiedAt`. Add a unit test.

### 🟡 The `ticket:corrected` bell notification links to `/meus-chamados`, `lib/notification-url.ts:16`

**Problem**: `getNotificationUrl` has no case for `ticket:corrected`, so a technician clicking the bell item lands on the default `/meus-chamados`, which is their own requested tickets. `NotificationsBell.getNotificationMeta` also has no case, so the item shows a generic icon and label. The spec says the link is `/chamados-atribuidos/[id]`. Only the toast's "Abrir" gets it right.
**Suggested fix**: Add `ticket:corrected` to `getNotificationUrl`, pointing at `/chamados-atribuidos/${ticketId}`, and to `getNotificationMeta`. Test it.

### 🟡 `corrigirServicoAction` silently ignores `novoTecnicoId` when the current technician qualifies, `app/(dashboard)/gestao/actions.ts:571-619`

**Problem**: `CorrigirServicoDialog` shows the eligible-technician picker for any service change on a chamado that has a technician. It doesn't check whether the current one already has the specialty. If the manager picks someone new, the action keeps the current technician, sends `ticket:corrected`, and returns `{ ok: true }`. The manager believes the technician was swapped.
**Suggested fix**: Either reject with a clear message when `novoTecnicoId` is sent but not needed, or only show the picker after the server says a technician is required, for example by exposing "current tech qualifies" from the eligible route.

### 🟡 The priority dialog's "desce" text is wrong for the Admin-with-technician case, `app/(dashboard)/gestao/_components/CorrigirPrioridadeDialog.tsx:71`

**Problem**: The text says lowering "dá o prazo cheio da prioridade nova, contado desde a classificação". With a technician assigned, which is the only case an Admin reaches that Preposto can't, the rule is `Dc + max(0, Tn − Tc)` from the current deadline.
**Suggested fix**: Branch the text on `hasTechnician`.

### 🟡 Several refusals write no `[revisao-ia]` line, `app/(dashboard)/gestao/actions.ts:267-276`, `:307`, `:521-537`, `:580-612`, `:1398-1452`

**Problem**: AC-17 asks for one line per confirmation or correction attempt, with `resultado: 'recusada'` on refusals. These refusals return without logging: not classified, same priority, `montarSnapshotCorrecao` failure, no service, same service, technician required, technician invalid or overloaded, and most reassignment validations.
**Suggested fix**: Log `recusada` on each early return, or route them through one helper.

## Nits

- ⚪ `app/(dashboard)/gestao/actions.ts:336`, `:643`, the filters use `status: { $in: ACTIVE_STATUSES }` instead of the exact status read. It's harmless today, because `validado → em atendimento` always changes `assignedToUserId`, but repeating `atual.status` matches the "repeat what you read" invariant literally.
- ⚪ `app/(dashboard)/gestao/actions.ts:1735`, `:1578`, `confirmarDecisoesIaAction` and `reassignTicketAction` send `e.message` to the UI, while the new priority and service actions correctly send a fixed phrase.
- ⚪ `app/(dashboard)/gestao/_components/RevisaoIaPainel.tsx:268`, every per-field failure, including `erro`, shows "O valor já mudou desde a última leitura", which is misleading for a transient error.
- ⚪ `app/(dashboard)/gestao/actions.ts:1472`, reassignment still stores the reason in `Chamado.reassignmentNotes`. It isn't exposed today (both `normalizeChamado` paths drop it), but the invariant says the reason lives only in `DecisaoIa` and `correcao_gestao`.
- ⚪ `app/(dashboard)/gestao/page.tsx` (mobile Sheet), the "Revisão da IA" `<label>` isn't associated with the control. The trigger has `aria-label`, so this is cosmetic.

## Strengths

- `montarSnapshotCorrecao` is a faithful, pure-ish encoding of the spec table. `now` is injected, it never throws, and it returns a patch where a missing field means "unchanged", so `computedAt`, `classifiedAt` and `responseStartedAt` can't be touched by accident. Its unit tests cover tight, loose and already-expired deadlines, 24x7 against business hours with holidays, and the "sobe without moving, then desce" zero-diff case.
- The priority and service `findOneAndUpdate` filters repeat the values read without any `$ne`. The "só o Admin baixa" rule is enforced by the role check plus `assignedToUserId` in the filter, so a concurrent assignment can't let a Preposto lower the priority.
- `ACOES_SO_DA_GESTAO` is applied as `action: { $nin }` inside the query, before the limit, on both read paths a Solicitante or Técnico can reach: `/api/chamados/[id]/history` and `lerLinhaDoTempo`. `assignment-history` is manager-only, and `classificationNotes` no longer receives the reason.
- `confirmarDecisao` is a genuine conditional update, with `confirmacao_ia` written only when `modifiedCount === 1`. Confirming twice, or in two tabs, doesn't duplicate anything.
- The decisions route correctly hides confidence, reason and `divergente` while a decision is still blind, which protects the calibration.

## Test coverage

Coverage is broad: unit tests for the snapshot rule, DB-backed atomicity tests for priority and service, AC-20 marker race tests, injected failures in each *wrapped* AC-21 step, and component tests for the panel and dialogs. The gaps match the findings:
- the monitor's escalation-insert race (only the marker race is tested);
- concurrent reassignments;
- failures in the unwrapped post-commit calls (`gestorUser` in the priority action, `previousTech` and `reatribuicao_tecnico` in reassignment);
- a legacy SLA with no `resolutionTargetMinutes` on the "desce com técnico" path;
- the `ticket:corrected` URL in `getNotificationUrl`;
- `novoTecnicoId` sent when the current technician qualifies.
