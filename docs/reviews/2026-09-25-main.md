# Review, main (uncommitted), 2026-09-25

**Reviewed by**: Sonnet 5 (`claude-sonnet-5`), fresh reviewer. The implementation is believed to be from opus; 43 of the added tests came from the same model family as the reviewer and were read with extra skepticism (see Test coverage).
**Scope**: 47 files (31 tracked + 16 untracked), uncommitted against `main` (HEAD 795257b). `.claude/agents/memory/code-reviewer/patterns.md` and `docs/scope/scope.md` ignored as housekeeping, so 45 files were reviewed.
**Verdict**: Changes requested

## Summary

Spec 0008 adds a synchronous, never-throwing step inside `confirmarAbertura` that picks a technician by rule (least load, tie by longest time without a new chamado), writes the assignment with the same atomic filter as the manual path, recounts the load after writing, undoes on overflow, and only then writes history, decision and notifications. The core module (`lib/chamados/atribuicao-automatica.ts`) is careful: the ordering guarantees (nothing external before the recount), the conditional undo, the idempotency through the `jaExistia` early return, and the leak surface for solicitante and tecnico are all sound, and I found no blocker in the concurrency or atomicity design. The one significant problem is on the read side of the chat: the sentence this change rewrites is recognized by exact text equality in `leitura.ts`, so every 0008 sentence (and the 0007 one) is drawn as the amber "AI failed, open the form" warning card instead of the success notice. The rest are minors: duplicated copy tables, a few vacuous or overclaiming tests, and small resilience gaps.

## Blockers

None.

## Major

### 🟠 The chat's "chamado aberto" notice is matched by exact text, so every 0008 sentence renders as the failure card, `app/(dashboard)/conversas/_lib/leitura.ts:120-133`

**Problem**: `lerChamadoEmLeitura` decides `chamadoAberto` with `item.dados.texto === fraseDeChamadoAberto(ticket_number)`, called with no options, which yields only the non-validated sentence ("aberto. Um Preposto vai analisar..."). `fraseDeChamadoAberto` (`lib/assistente/mensagens.ts:86-107`) now has four shapes (0007 validated, 0008 atribuido, 0008 sem_tecnico, non-validated) and `confirmar.ts:304-309` writes whichever applies. Only the last one matches. For the other three, `PainelChamado.Item` falls through to `CartaoSistema` (`Mensagens.tsx:95`), which is the amber card with a warning triangle and the "Abrir por formulário" link, documented as the fallback for "the AI did not answer". So right after "o técnico Carla já foi designado", the solicitante sees a warning card that offers the manual form. The 0007 commit (64f0dc8) introduced the mismatch without touching `leitura.ts`; the existing `leitura.test.ts` only feeds the base sentence, which is why nothing caught it.
**Why it matters**: Pre-existing since 0007, but 0008 is the change that rewrites this sentence, adds two more variants that all fall on the wrong branch, and turns the feature-on path (validated and assigned) into the default success path of the chat. AC-12 is met textually and the runtime check would not flag it, yet the presentation contradicts the message and invites a duplicate chamado through the form.
**Suggested fix**: Stop inferring the kind from prose. Persist a marker on the message (a `payload.tipo`/subtype on the `ConversaMensagem` written by `confirmarAbertura`) and read that in `leitura.ts`, or at minimum build the match from a helper that recognizes all four variants (for example a `ehFraseDeChamadoAberto(texto, ticketNumber)` that lives next to `fraseDeChamadoAberto`). Add a `leitura.test.ts` case per variant, and a `PainelChamado` test that a validated-and-assigned sentence renders the success notice.

## Minor

### 🟡 Three parallel copies of the same copy tables, `lib/chamados/novo-chamado.ts:52-70`, `lib/email/templates.ts:41-57` and `82-93`, `components/realtime/RealtimeProvider.tsx:200-212`

**Problem**: The manager-side text for "validado e atribuído a X / validado, sem técnico disponível / validado automaticamente" is written three times (persisted title, email subject, toast), and the technician-side "automaticamente" variant three more times (`tituloDaNotificacaoDeAtribuicao`, two inline `assignedBy?.id === ATRIBUIDO_POR_SISTEMA.id` checks in `templates.ts:49,82`, and `RealtimeProvider.tsx:118`). The predicate `atribuidoPeloSistema` exists but only `notificar-atribuicao.ts` uses it.
**Why it matters**: AC-13 and AC-11 pin the same wording in every channel. Any copy tweak has to be made in three places and the tests only check each channel independently, so drift is silent.
**Suggested fix**: Move the pure title builder (`atribuicao` payload to text) and the `atribuidoPeloSistema` predicate into `shared/` (both `RealtimeProvider` and the server modules can import it) and have the three call sites use it.

### 🟡 The lost-acknowledgement case is not covered by the undo or the orphan log, `lib/chamados/atribuicao-automatica.ts:258-279`

**Problem**: `ctx.gravadoPara` is set only after `findOneAndUpdate` returns a document. If the server applies the write and the driver throws (socket timeout, failover with `retryWrites` exhausted), `gravadoPara` is still `null`, so `marcarErro` uses the `semTecnico` filter, which no longer matches, returns `nao_tentada`, and logs nothing. The chamado is left assigned without history, decision or notification and without the `estado: 'orfao'` line the spec promises.
**Why it matters**: It is the exact orphan state AC-4 wants to be visible, and this variant is silent. It needs an unusual failure, so severity is low.
**Suggested fix**: Set `ctx.gravadoPara = candidato` before the write. The undo filter is conditional on `assignedToUserId` and `atribuicaoAutomatica.resultado`, so trying it after a write that never happened simply matches nothing.

### 🟡 A stale `atribuicaoAutomatica: atribuido` marker survives the "someone else took it" exit, `lib/chamados/atribuicao-automatica.ts:302-305`

**Problem**: When the recount finds `meu === 0` (a gestor reassigned or the chamado left the load statuses in the window), the function returns `nao_tentada` without clearing the marker it wrote. The chamado then carries `resultado: 'atribuido'` and `tecnicoId` of a technician who was never notified and never got a history line or decision, and the gestão detail will read "Atribuído automaticamente a X".
**Why it matters**: The window is a few milliseconds and needs a reassignment inside it, so it is rare, but the marker is a claim shown to Preposto and Admin and it would be false.
**Suggested fix**: In that branch, clear only the marker with a conditional update (`atribuicaoAutomatica.tecnicoId` equal to the candidate and `resultado: 'atribuido'`), leaving the manager's fields alone.

### 🟡 Requester-typed title goes raw into HTML email, now to technicians without triage, `lib/email/templates.ts:82-93`

**Problem**: The diff adds `escapeHtml` for the technician name, but `p.title`, `p.ticketNumber` and `recipientName` in the same strings are still interpolated raw. For chat chamados the title includes `localExato`, free text from the solicitante (`montarTituloChat`). Pre-existing pattern, but the automatic path now delivers it to the technician's inbox with no Preposto in between.
**Why it matters**: HTML injection into an internal mail (link or content spoofing). Mail clients strip scripts, so the realistic impact is phishing-style content.
**Suggested fix**: Escape `title` (and the other interpolated fields) once at the template boundary, using the helper that now exists in the file, and add a test with an HTML title next to the existing name test.

### 🟡 Vacuous or overclaiming tests (several from the sonnet batch)

- `lib/chamados/__tests__/atribuicao-criterio.test.ts:217`, "nunca passa do limite da decisão, mesmo com números enormes": with those inputs the sentence is 156 characters, and even with `Number.MAX_SAFE_INTEGER` everywhere it is 195, below `DECISAO_MOTIVO_MAX = 200`. The test cannot fail if the `slice` in `montarMotivoTecnico` is removed. It proves nothing about the cap (and the cap is unreachable dead code today).
- `lib/chamados/__tests__/atribuicao-automatica.db.test.ts:454`, "quem nunca recebeu chamado vem primeiro no empate": the load decides (`comHistorico` has 1, the other two have 0) and the two zero-load technicians tie on id, so null-first is not exercised at DB level. Only the pure unit test covers it.
- `lib/chamados/__tests__/atribuicao-automatica.db.test.ts:344`, "nunca entra na calibragem": `medirCalibragem` only reports `servico` and `prioridade`, and `decididoPor: 'ia'` plus `efeito: 'sugestao'` already exclude the row, so the assertion passes even if the `campo` filter disappears.
- `app/(dashboard)/gestao/__tests__/atribuicao-automatica.db.test.ts:451`, race test: the comment says both paths had their turn, but the assertion `automatico + manual === 20` is true by construction because the loop counts every round in one branch or the other. If one side always wins, the loser branch is never exercised and the test still passes. I could not measure the distribution without writing a file. Assert that both counters are above zero, or force each interleaving with a hook.
- `shared/chamados/__tests__/atribuicao-automatica.constants.test.ts:33,37`: assert that constants equal their own literals (`ATRIBUICAO_TENTATIVAS_MAX` is 3, the tuple has two values). The behavior test in the DB file already pins the 3-attempt limit.
  **Why it matters**: They add green without adding protection.
  **Suggested fix**: Give each a case that can fail or delete it. For the cap, the sentence cannot reach 200 characters with any numeric input, so drop the dead `slice` and its test (or lower the cap under test). For the race test, assert that both counters are above zero or force each interleaving. For the two DB criterion tests, add a case where two technicians tie on load and only one has an aggregated row.

### 🟡 No parallel auto-versus-auto test of the load invariant, `lib/chamados/__tests__/atribuicao-automatica.db.test.ts:999-1109`

**Problem**: AC-8 is covered only through the deterministic `aposGravar` hook (a second chamado is inserted by hand between write and recount). No test runs several `tentarAtribuicaoAutomatica` calls with `Promise.all` against one technician at `limite - 1` and asserts that the final load never exceeds the limit. The hook proves the recount logic, not that the write-then-recount protocol holds under real interleaving (for example that two concurrent steps cannot both confirm at limit + 1).
**Why it matters**: The whole design rests on that protocol because the database is a standalone Mongo without transactions.
**Suggested fix**: Add a property-style test: N parallel steps, one technician with `maxAssignedTickets = k`, repeated rounds, assert final `carga <= k` and that every confirmed step has its history, decision and notification.

## Nits

- ⚪ `lib/chamados/__tests__/atribuicao-automatica.db.test.ts:966`, the "desfazer não acha o documento" test builds a state (marker mutated by hand) that the module itself cannot produce; it pins the guard, fine, but the comment should say it is a defensive branch.
- ⚪ `lib/chamados/__tests__/atribuicao-automatica.db.test.ts:1068`, the comment says "limite 1" while the technicians are created with `maxAssignedTickets: 2`.
- ⚪ `app/(dashboard)/gestao/__tests__/atribuicao-automatica.db.test.ts:205`, the comment says Diego already has load, but no load is created; the assertions do not depend on who is chosen.
- ⚪ `app/api/gestao/chamados/__tests__/route.test.ts:496`, pins `em: ''` as the shape when the date is missing. The schema makes `em` required, so the sentinel is unreachable and typed as `string`; drop the case or make `em` nullable.
- ⚪ `lib/chamados/atribuicao-criterio.ts:67`, the reason says the tie was "decidido por quem está há mais tempo sem receber" even when every tied technician has `ultimaAtribuicao` null and the id decided.
- ⚪ `lib/chamados/novo-chamado.ts:100`, body reads `${titulo}. Motivo: ...` and produces a double period when the title already ends in punctuation.
- ⚪ `lib/chamados/notificar-atribuicao.ts:66-71`, the two `emitToRoom` calls are sequential; with the socket-server down the automatic path adds up to 2 x 1200 ms to the solicitante's confirmation (they cannot throw, so parallelizing is safe). Also, one `NotificationModel.create` failure skips both live events and the email, which is coarser than the "one try per effect" wording of the spec.
- ⚪ `lib/chamados/atribuicao-automatica.ts:78`, the test seam `aposGravar` is part of the production parameter type (the spec asks for it). A `/** @internal */` tag or a separate exported test-only wrapper would keep callers from passing it.
- ⚪ `AGENTS.md` files (`lib/assistente`, `lib/ia-confianca`, `app/(dashboard)/gestao`) still describe the world before 0008 (for example "nenhuma fatia lê este valor"). The spec defers this to `/sync`, noted only so it is not forgotten.
- ⚪ Design consideration for whoever flips the switch: the human triage that used to sit between a solicitante and a technician's queue is gone, and there is no per-requester cap. The per-user LLM limit throttles chat turns but not confirmed chamados, so one requester can fill the limit of every technician of a specialty. Worth an alert on `sem_vaga` volume in the first weeks.

## Strengths

- The order of effects in `tentarAtribuicaoAutomatica` is right: conditional write with the manual path's own filter, recount that also checks the chamado is still this one, undo with an ownership filter, and no history, decision, notification, email or event before the recount passes. Every unhappy exit maps to `nao_tentada` or `sem_tecnico` with a clear rule for who owns the state, and `confirmarAbertura` wraps the call defensively as well.
- Data exposure is handled in depth: explicit projections, DTO whitelists that never spread the document, a role check in `ChamadoDetailSheet` that fails closed for `null`, a history sentence with no id, motive or load, and a real-Mongo visibility suite with a positive control proving there was something to leak.
- The manual path is untouched behaviorally: `notificarAtribuicao` reproduces the same payload, `actions.test.ts` is unchanged, and a dedicated test pins payload, order and error propagation.
- The DB suite for the module is strong where it counts (failure injected at each moment, orphan log, effect isolation, breach computed from the same helper). The idea of running the orphan query from the source comment against Mongo caught a real bug (`$id` versus `$$id`), even if the mechanism is brittle.
- The switch defaults off, does not depend on `PROMPT_VERSION`, and the Zod field is required on purpose so an old form fails loudly instead of silently disabling the flag.
